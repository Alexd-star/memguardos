# 01 赛题讲解

## 1.1 赛题一句话解释

这个赛题要求做一个“面向 Linux 的智能体记忆系统”。所谓智能体，可以理解为会帮你操作电脑、执行命令、读文件、改配置、查日志、写代码的 AI 助手。这样的助手如果长期工作，会看到很多信息：你的偏好、常用命令、系统配置、工具报错、修复经验、文件路径、日志和隐私数据。赛题关注的问题是：这些信息哪些应该被记住，哪些不应该被记住，后续怎么检索出来帮助 AI 工作，用户说“忘掉某些信息”时系统能不能真正忘掉，并且能不能在 Linux/openKylin 环境中运行和验证。

MemGuardOS 的回答是：把多源输入变成结构化记忆，先做敏感治理，再做轻量存储、混合检索、RAG 上下文构建和精准遗忘，同时接入 systemd、cgroup、auditd、Kylin SDK、Peony/UKUI、BPF LSM 等 Linux/openKylin 机制，形成一条可运行、可测试、可审计的闭环。

## 1.2 赛题要解决的问题

普通聊天记录只是把对话按时间保存下来。它不知道“以后回答 Linux 命令时直接给命令”是一条长期偏好，也不知道“systemd 服务内存限制要看 MemoryMax 和 cgroup”是一条知识，更不知道 `.ssh/id_rsa`、API key、手机号、身份证等不应该进入长期记忆。更麻烦的是，当用户说“忘掉 temporary project codename”时，如果系统只是删除数据库里一行，而旧明文还留在索引、段文件或日志里，那么这并不是真正可靠的遗忘。

赛题的核心问题可以拆成四句话：

1. 从 Linux/Agent 工作过程里提取有价值的偏好和知识。
2. 检索时能把相关记忆交给上游 LLM 或 Agent，而且上下文要可解释、可脱敏。
3. 遗忘时不能只做表面删除，要能定位候选、确认删除、清理索引、压缩存储并验证。
4. 作品不能只停留在普通应用层，要体现 openKylin/Linux 操作系统机制。

## 1.3 输入是什么

MemGuardOS 支持的输入不是单一文本，而是多源输入：

| 输入类型 | 通俗解释 | 项目入口 |
|---|---|---|
| 普通文本 | 用户手动告诉系统一条偏好或知识。 | `memctl ingest --text` |
| 文件内容 | 从一个文本文件中读取内容并导入。 | `memctl ingest --file` |
| 结构化配置 | JSON/YAML 形式的用户偏好、项目配置。 | `memctl ingest-config` |
| shell history | 用户或 Agent 过去执行过的命令。 | `memctl ingest-history` |
| 工具执行结果 | 比如 pytest、systemctl、journalctl 的命令、退出码、输出。 | `memctl ingest-tool-result` |
| OS 事件 | 文件访问、敏感路径读取、服务事件等。 | `memctl ingest-os-event` |
| auditd 日志 | Linux 审计系统采集的敏感路径访问日志。 | `memctl ingest-auditd` |
| Web 控制台输入 | 浏览器本地页面提交记忆、检索、遗忘请求。 | `memctl web` |
| Unix socket API | 本地 Agent 用 JSON 请求调用服务。 | `memguard/api/server.py` |

## 1.4 输出是什么

项目的输出分为“功能输出”和“证据输出”。

功能输出包括：

1. 记忆写入结果：是否存储、记忆 ID、类型、子类型、质量分、敏感等级。
2. 检索结果：命中的记忆、分数、来源、层级、敏感状态。
3. RAG 上下文包：给 LLM 生成回答前使用的记忆上下文、来源分布、选择轨迹、token 预算。
4. 遗忘计划和执行结果：候选记忆、匹配原因、确认后删除情况、compact 后验证结果。
5. 审计链结果：关键操作的审计记录和哈希链校验结果。
6. 诊断报告：系统环境、namespace、存储、SDK、OS 机制、审计状态。

证据输出包括：

1. `docs/eval_result.json` 和 `docs/eval_report.md`：本地评测结果。
2. `docs/evidence/latest/`：openKylin 证据包。
3. `docs/competition_ready.json` 和 `docs/竞赛就绪自检报告.md`：竞赛就绪检查。
4. `dist/memguardos_competition_submission_*.zip`：正式提交包。
5. Web 控制台截图、终端运行截图、openKylin 桌面插件截图。

## 1.5 评判标准用人话怎么理解

评委通常不会只看“能不能搜索一段文本”。他们会看：

| 评判方向 | 人话解释 | MemGuardOS 对应能力 |
|---|---|---|
| 需求覆盖 | 赛题要求的核心功能有没有做全。 | 多源记忆、检索、RAG、遗忘、OS 机制。 |
| 正确性 | 功能是不是真能跑，结果是不是合理。 | 70 passed、本地评测、openKylin 证据。 |
| 可复现 | 换个环境能不能按步骤跑出来。 | README、部署手册、脚本、证据包、提交包 smoke。 |
| 创新性 | 是否只是普通 RAG，还是有 OS/记忆/遗忘亮点。 | 程序性记忆、层次图谱、审计链、BPF LSM、Peony/UKUI。 |
| 端侧部署 | 是否轻量，不强依赖 GPU、外部 API、重型数据库。 | Python + SQLite + mmap，Kylin SDK 可选增强。 |
| 安全性 | 是否处理敏感信息和遗忘残留。 | 敏感阻断、脱敏、tombstone、compact、verify-forget。 |
| 工程完整度 | 是否像一个能交付的项目。 | CLI、daemon、Web、systemd、.deb、测试、文档、GitHub。 |

## 1.6 必须实现哪些功能

对这个项目来说，必须实现并能讲清楚的功能是：

1. 偏好记忆提取：识别用户偏好，比如回答风格、工具选择、输出格式。
2. 知识记忆提取：识别可复用事实、流程、故障修复经验。
3. 敏感治理：阻断高风险内容，脱敏中低风险内容。
4. 轻量存储：用本地文件和 SQLite 保存，适合端侧部署。
5. 混合检索：不是只按关键词，而是结合 FTS、hash-vector、图谱、跨语言 token。
6. RAG 上下文构建：把相关记忆整理成可交给 LLM 的上下文包。
7. 精准遗忘：自然语言请求、候选、确认、tombstone、索引清理、compact、验证。
8. 审计链：记录关键操作并能验证是否被篡改。
9. Linux/openKylin 机制：systemd、cgroup、auditd、Kylin SDK、Peony/UKUI、BPF LSM 测试路径。
10. 测试和证据：自动测试、评测报告、证据包、提交包审计。

## 1.7 一定不要夸大的点

答辩时要诚实表达，不能把已做的原型说成不存在的企业平台：

1. 默认抽取器是可解释规则和轻量语义信号，不是默认调用大模型。
2. Kylin SDK 已有真实推理和可选增强证据，但默认仍保留 fallback，不能说所有检索都强制依赖 SDK。
3. BPF LSM 是安全测试路径，验证了指定测试文件强制拒绝，不能说已经生产级拦截全系统敏感路径。
4. Peony/UKUI 有可见入口和 smoke 证据，但不是完整商业桌面安全中心。
5. Web 控制台是本地运维页面，不是公网 SaaS 管理后台。
6. 当前没有完整企业 RBAC、SSO、多租户权限系统。
