# MemGuardOS 答辩稿

本文为 MemGuardOS 正式答辩讲解稿，适合 8-12 分钟现场答辩，也可压缩为 5 分钟路演版本。答辩时建议配合 `docs/答辩提纲.md` 制作 PPT，配合 `docs/演示视频脚本.md` 录制 3-5 分钟演示视频。

## 1. 开场陈述

各位老师好，我们的作品是 **MemGuardOS：面向 Linux 的智能体记忆提取与精准遗忘机制**。这个项目对应研究生操作系统开源创新大赛赛题 3，目标是在 openKylin/Linux 环境下，为 OS Agent 提供一套本地可运行、可测试、可审计、可精准遗忘的记忆基础设施。

我们对这个赛题的理解是：它并不是要求做一个普通的聊天记录库，也不只是把文本塞进向量数据库做 RAG。OS Agent 在真实系统中会长期处理用户偏好、命令历史、配置文件、工具执行结果、系统日志和潜在敏感凭据。这样一来，系统必须回答四个问题：第一，哪些内容应该沉淀为长期偏好或知识；第二，生成回答前如何检索到可靠、脱敏、可控长度的上下文；第三，用户要求忘掉某类信息时，系统如何做到可验证删除；第四，如何体现 Linux/openKylin 的操作系统机制，而不是只做应用层字符串处理。

围绕这些问题，我们实现了 MemGuardOS。它默认不依赖 GPU、不依赖外部 LLM API，也不依赖重型向量数据库，使用 mmap 追加式段文件、SQLite FTS、稳定 hash-vector、图谱关联和审计哈希链构成轻量主链路。同时，项目集成了 systemd/cgroup、journald、auditd、BPF LSM 安全测试拦截、UKUI/Peony 原生插件源码和 Kylin SDK 探测，保证作品能够在 openKylin 上复验。

## 2. 问题背景

随着大模型智能体进入操作系统场景，Agent 不再只是回答一句话，而是会持续执行命令、读取配置、调用工具、分析日志、修复系统问题。它需要记住用户偏好的输出风格，例如“回答 Linux 命令时直接给命令和风险提示”；也需要记住知识和工作流，例如“systemd 服务异常时先看 journalctl，再检查 cgroup 限制”；还会接触敏感信息，例如 token、私钥路径、账号文件和审计日志。

如果没有专门的记忆管理，系统会出现几个风险。第一，记忆质量不可控，临时上下文和长期偏好混在一起。第二，RAG 检索可能把敏感信息直接送给模型。第三，用户说“忘掉某项目代号”时，如果只是从搜索结果中隐藏，旧明文仍然可能残留在文件或索引中。第四，系统没有 OS 级证据，无法证明它适合 Linux 端侧部署。

因此，我们把 MemGuardOS 设计成一个面向 OS Agent 的本地记忆系统。它既提供 Agent 可用的检索和上下文构建能力，也提供操作系统视角下的隔离、审计、资源控制和安全增强。

## 3. 系统目标

我们的设计目标可以概括为六点。

第一，多源融合。系统支持从文本、文件、结构化配置、shell history、工具执行结果、OS 事件、journald 和 auditd 日志中提取记忆。

第二，结构化建模。系统将记忆分为偏好记忆、知识记忆和敏感策略记忆，并进一步标注子类型、来源、层级、实体、关系、版本、敏感标签和审计信息。

第三，轻量可复现。默认主链路使用 mmap 和 SQLite，在普通虚拟机上就能运行；不把比赛复验绑定到云端模型、GPU 或付费服务。

第四，安全可控。系统在写入前检测敏感信息，在输出 RAG 上下文前再次脱敏，并把关键操作写入审计哈希链。

第五，精准遗忘。系统支持自然语言定位遗忘候选，经过 dry-run 和确认后删除，并在 compact 后验证明文是否仍然存在。

第六，OS 机制集成。项目不只提供 Python 逻辑，还集成 systemd、cgroup、journald、auditd、BPF LSM 和 UKUI/Peony 原生插件源码，体现赛题中的 Linux/openKylin 属性。

## 4. 总体架构

MemGuardOS 的整体架构可以分成五层。

第一层是多源接入层。它接收文本、文件、配置、shell 行为、工具结果和 OS 事件。所有输入先经过清洗和质量校验，包括 Unicode 标准化、空输入拒绝、低质量提示和质量分审计，避免把噪声直接变成长期记忆。

第二层是安全与抽取层。系统先进行敏感检测和脱敏，然后把输入抽取成偏好、知识或安全策略记忆。默认抽取器是端侧可解释的 deterministic semantic extractor，会记录 `method`、`signals` 和 `confidence`，便于答辩时说明“为什么这条记忆被判定为偏好或知识”。如果环境中明确配置了 `MEMGUARD_EXTRACTOR_COMMAND`，也可以接入本地 NER 或 LLM JSON 增强器；增强器失败时会自动回退。

第三层是存储层。正文进入 mmap 追加式段文件，元数据进入 SQLite。SQLite 中同时管理 FTS 全文索引、版本记录、图谱边和审计哈希链。这个选择的好处是端侧轻量、可解释、易复验，而且 compact 后可以做明文泄漏探针。

第四层是检索和上下文层。系统结合 SQLite FTS、稳定 hash-vector、图谱实体召回、跨语言技术词扩展和冲突解决，支持普通检索、图谱检索、Agent 批量检索和 RAG 上下文构建。生成前上下文会经过脱敏、排序、裁剪和 token 预算估算。

第五层是治理和 OS 集成层。这里包括精准遗忘、namespace 隔离、systemd/cgroup 资源限制、journald/auditd 事件接入、BPF LSM 可选强制拦截、UKUI/Peony 插件源码、本地 Unix socket API 和 Web 控制台。

## 5. 核心功能讲解

### 5.1 多源记忆提取

MemGuardOS 支持多种输入入口。文本和文件可以通过 `memctl ingest` 写入；结构化配置可以通过 `ingest-config` 展开为配置记忆；shell history 可以被解析为用户行为记忆；工具执行结果可以转换为工具轨迹和修复案例；OS event 和 auditd 日志可以进入安全策略和系统事件记忆。

这种设计的价值是：OS Agent 的记忆不再只来自对话，而是来自真实的系统使用过程。例如一次 systemd 服务失败、一次 pytest 修复、一次 auditd 发现私钥访问，都可以成为之后 Agent 决策的依据。

### 5.2 偏好、知识和安全策略记忆

系统中的记忆卡片包含类型、子类型、层级、来源、实体、关系、敏感标签、版本和审计信息。偏好记忆包括输出风格、工具偏好、安全偏好等；知识记忆包括工作流、案例、模板和工具轨迹；敏感策略记忆包括“不要保存某类 token”“某路径属于高风险路径”等安全规则。

这种结构化建模让系统可以回答三个问题：它记住了什么、为什么记住、后续应该怎么用。

### 5.3 混合检索和 RAG 上下文

检索层不是单一关键词搜索，而是融合了 FTS、稳定 hash-vector、图谱实体召回和冲突解决。对于中文问题检索英文 Linux 技术记忆，系统通过技术词扩展和实体召回提升跨语言召回。对于多个互相冲突的偏好，系统会结合主题、更新时间和重要性进行冲突处理，避免把矛盾指令都塞进 prompt。

当上游 Agent 需要调用 LLM 时，可以使用 `build-context` 或 `build-prompt` 得到已脱敏的上下文包。这个包包含候选记忆、来源、敏感标记和 token 预算估算。也就是说，MemGuardOS 是在 LLM 生成前提供可靠上下文，而不是一定要自己调用外部模型。默认情况下它不需要购买 LLM API。

### 5.4 精准遗忘

精准遗忘是本项目最重要的能力之一。我们的流程是：

```text
自然语言请求 -> dry-run 候选 -> 用户确认 -> tombstone -> FTS/图谱清理 -> compact -> 泄漏探针验证
```

例如用户说“忘掉 temporary project codename”，系统先展示可能删除哪些记忆；用户确认后，系统不只是让搜索结果不显示，而是写入墓碑、清理元数据索引、清理图谱关系，并在 compact 后检查段文件和元数据中是否还存在目标明文。

这条链路对应赛题中的“精准遗忘机制”。它强调的是可控、可审计、可验证，而不是简单删除一行数据库。

### 5.5 敏感治理

系统内置了多类敏感检测规则，包括邮箱、手机号、身份证、银行卡、API Key、token/password/secret、private key、中文姓名、中文地址和 OS 高风险路径。高风险内容会被阻断，中低风险内容会脱敏后保存。用户也可以添加自定义正则，或者用受限自然语言生成敏感规则。所有敏感规则变更都会进入审计链。

这种设计适合 OS Agent，因为它会接触比普通聊天更多的系统级敏感信息，例如 `.ssh/id_rsa`、`/etc/shadow` 相关事件、服务日志中的 token 等。

### 5.6 多会话隔离和后台服务

MemGuardOS 支持 namespace 隔离。不同 namespace 拥有独立段文件、SQLite 元数据库、敏感规则和审计链，避免不同项目或不同用户会话的记忆互相污染。在 openKylin 上，我们还配置了 `memguardd@demo-a` 和 `memguardd@demo-b` 这样的 systemd 模板服务，让不同 namespace 拥有独立服务实例和 cgroup。

后台服务通过 Unix domain socket 提供 JSON API，供本地 Agent 调用。API 覆盖 health、ingest、search、batch_search、build_context、forget、audit 等能力。

## 6. 操作系统机制说明

为了体现操作系统赛题属性，我们重点实现和验证了以下机制。

第一，mmap 段文件。记忆正文追加写入 segment 文件，读取时使用 mmap。compact 后可以从物理文件层面验证旧明文是否残留。

第二，SQLite FTS 和图谱。SQLite 负责元数据、全文索引、版本、图谱边和审计链，既轻量又便于 openKylin 端侧部署。

第三，systemd/cgroup。我们提供 `memguardd.service` 和 `memguardd@.service`，并设置 `MemoryMax=512M`、`CPUQuota=50%` 等资源限制。openKylin 证据显示相关服务处于 active，模板服务拥有独立 cgroup。

第四，journald 和 auditd。记忆操作可以写入 journald；auditd 敏感路径日志可以被解析为 OS event 并进入记忆系统。

第五，BPF LSM。项目提供 BPF LSM `file_open` 安全测试路径，在 openKylin 上验证了对 `/tmp/memguardos_lsm_secret` 的强制拒绝，并支持从 JSON 策略生成可审查静态 denylist。这里我们保持准确边界：默认只拦截安全测试文件，不拦截 `/etc/shadow`、SSH、sudo 或 PAM 链路，避免破坏系统登录。

第六，UKUI/Peony。项目提供 Peony 右键菜单插件、UKUI 控制中心插件和 UKUI 托盘源码，已在 openKylin 上完成构建验证。Peony 入口不是简单的一键导入，而是先生成多文件扫描预览，展示敏感风险、建议动作和是否可导入，再由用户确认后执行写入；manifest 带签名、文件指纹、过期时间和 nonce，可以防止预览后篡改或重复执行。UKUI 控制中心入口“MemGuardOS 记忆安全”面向本机管理员，提供服务状态、服务级 cgroup、Kylin SDK、审计链、Polkit 高权限动作、诊断导出和本地控制台入口。托盘提供低干扰状态提醒和快捷入口，退出托盘不会停止核心服务。

第七，Kylin SDK。系统提供 Kylin embedding SDK 和 vector SDK 探针，embedding 可作为可选重排后端；默认仍保留 FTS/hash/graph fallback，以保证跨环境复现。

## 7. 评测结果

项目当前测试和评测结果如下。

最新 openKylin 全量测试为 `294 passed`。通用 `217` 条 benchmark 用例/种子上，类型识别准确率、平均 Recall@5、跨语言 Recall@5、敏感阻断 F1、精准遗忘候选精确率和召回率、冲突处理正确率均为 `1.0000`。独立的 `200` 条用户-Agent 抽取专项中，提取精确率、召回率、F1、遗忘成功率和跨会话遵循率均为 `1.0000`，角色污染率和敏感泄漏率为 `0`。

为了回答“记忆是否真正帮助 Agent”，我们又增加了双层价值评测。16 组固定配对实验中，任务完成率由 `0.7500` 提升至 `1.0000`，首选工具准确率由 `0.3846` 提升至 `1.0000`，交互轮数平均减少 `1.4375`，相对完整历史回放的 Prompt token 估算减少 `61.1264%`。原 12 组真实 OpenHands 会话、新增 R13-R20 扩展会话和 8 组 holdout 留出盲测合计 28 组全部完成，记忆系统层和 Agent 行为层均为 `28/28`。为克服 1.7B 模型偶发的格式与工具规划偏差，适配层增加了偏好执行 Hook、一次有界合规修复、严格只读结构化意图恢复和程序性结果兜底；每次恢复都有来源字段，不能表述为模型原生能力。

性能方面，优化后 openKylin 10k 负载 P95 为 `10.105 ms`，P99 为 `75.255 ms`，RSS 为 `130444 KB`；独立三轮 6 worker 并发试验最差 P95 为 `54.381 ms`，完整 10k 评测内并发 P95 为 `139.264 ms`，Agent 批量检索 P95 为 `11.699 ms`。统一消融中纯文本 Recall@5 为 `0.8426`，混合检索和完整系统为 `1.0000`。这不仅证明延迟低于 500 ms，也证明混合检索带来的召回提升不是口头判断。

当前本地 benchmark 覆盖 59 条种子记忆、54 条检索样例、31 条敏感检测样例、29 条遗忘样例、10 条冲突样例、19 条图谱样例、6 条质量校验样例和 9 条程序性记忆样例；openKylin 最新证据包保留 53/48/31/25/10/17/6/7 的实机复验规模。样例中包含真实风格 auditd 日志、shell history、工具调用结果、OOM、BPF、UKUI、Web 和语义抽取边界。

这些指标我们不把它夸大成通用大规模公开数据集结论，而是表述为“在当前公开随包 benchmark 和 openKylin 证据包上的可复验结果”。这样更严谨，也更符合工程作品答辩口径。

## 8. 现场演示讲解词

现场演示建议控制在 3-5 分钟，按以下顺序进行。

第一步，展示项目入口和环境。

```bash
python -m pytest -q
python scripts/demo_smoke.py
```

讲解词：这里先展示单元测试和端到端 smoke demo，证明项目不是静态文档，而是可以实际运行的系统。

第二步，展示多源写入和检索。

```bash
python -m memguard.cli.memctl ingest --text "以后回答 Linux 命令时直接给命令和风险提示。"
python -m memguard.cli.memctl search "Linux 命令回答偏好"
```

讲解词：这条输入会被抽取为偏好记忆，后续 Agent 查询相关任务时可以召回。

第三步，展示可解释抽取。

```bash
python -m memguard.cli.memctl explain-extraction --text "真实案例：systemd service failed with exit_code=1，修复后运行 pytest。"
```

讲解词：系统会输出抽取方法、信号和置信度，说明为什么它被判定为某类知识或工具轨迹。

第四步，展示 RAG 上下文。

```bash
python -m memguard.cli.memctl build-context "openKylin 服务内存限制" --top-k 5 --token-budget 1200
```

讲解词：这里得到的是交给上游 LLM 之前的上下文包，已经经过排序、脱敏和 token 预算控制。

第五步，展示精准遗忘。

```bash
python -m memguard.cli.memctl forget "忘掉 temporary project codename"
python -m memguard.cli.memctl forget "忘掉 temporary project codename" --yes --compact
python -m memguard.cli.memctl verify-forget "temporary project codename"
```

讲解词：第一条是 dry-run，第二条确认删除并 compact，第三条验证旧明文是否仍存在。

第六步，展示 OS 证据。

```bash
systemctl status memguardd --no-pager
systemctl show memguardd -p MemoryMax -p CPUQuotaPerSecUSec
python -m memguard.cli.memctl verify-audit
```

讲解词：这里证明系统不是单进程脚本，而是具备 daemon、cgroup 资源约束和审计链验证。

第七步，如时间允许，展示本地 Web 控制台。

```bash
python -m memguard.cli.memctl web --host 127.0.0.1 --port 8765
```

讲解词：Web 控制台用于评审现场快速查看状态、写入、抽取解释、检索、RAG 上下文、遗忘、审计和系统诊断。

## 9. 创新点总结

我认为 MemGuardOS 的创新主要体现在四个方面。

第一，它把智能体记忆和操作系统机制结合起来。很多记忆系统只关注 embedding 和向量检索，而本项目把 systemd/cgroup、auditd、journald、mmap、BPF LSM、UKUI 和 Unix socket 都纳入可验证链路。

第二，它把精准遗忘做成可审计、可验证的流程。系统不是简单删除搜索结果，而是经过 dry-run、确认、tombstone、索引清理、compact 和泄漏探针验证。

第三，它适合端侧和比赛复验。默认不依赖外部 API、GPU 或重型数据库，openKylin 虚拟机即可运行；同时保留 Kylin SDK 和本地 NER/LLM 增强入口。

第四，它面向真实 OS Agent 使用场景。系统支持批量检索、上下文预算、敏感脱敏、工具结果、shell 行为和系统日志，这些都是智能体在操作系统上执行任务时真正需要的能力。

## 10. 准确边界主动说明

为了保证答辩表述严谨，我们会主动说明几个边界。

第一，默认抽取器是端侧可解释抽取，不宣称默认使用大模型语义抽取。我们这样设计是为了保证 openKylin 复验稳定、离线可运行、指标可复现。系统保留了本地 NER/LLM JSON 增强入口，后续可以替换或融合更强模型。

第二，Kylin embedding SDK 是可选增强，不是唯一主路径。系统已具备 SDK 探针和可选重排证据，但默认 FTS/hash/graph fallback 保证在 SDK 不存在或超时时仍然可用。

第三，BPF LSM 当前默认只拦截安全测试文件，证明机制可行，不默认拦截登录链路或系统关键文件。这样做是为了避免破坏评审环境。

第四，UKUI/Peony 插件已经完成源码和 `.so` 构建证据，Peony 右键菜单和 UKUI 控制中心入口均已在 openKylin 桌面完成可见验证，`.deb` 也已构建并在 openKylin 维护模式完成 apt 安装复验。这里仍需准确说明：当前参赛交付已经具备安装包证据；若进入长期产品化发行，还可以继续申请 openKylin 官方扩展或软件源渠道。

第五，Web 控制台是 localhost 演示和调试入口，不是公网 SaaS 多租户管理台。项目定位是本地 OS Agent 记忆模块。

这些边界并不影响赛题核心要求，反而说明我们把可复现主链路和可选增强路径做了清晰区分。

## 11. 可能问答

### 11.1 为什么不用外部大模型直接做抽取？

答：赛题要求的是面向 Linux 的记忆提取与精准遗忘机制，核心是系统机制、数据治理和可复验闭环。外部大模型可以增强抽取效果，但如果把主链路绑定到云 API，评审复验会受网络、额度、模型版本和费用影响。我们默认采用端侧可解释抽取，保证 openKylin 可离线运行；同时提供 `MEMGUARD_EXTRACTOR_COMMAND`，可以显式接入本地 NER 或 LLM JSON 增强器。

### 11.2 你们的 1.0000 指标是不是过拟合？

答：我们不会把当前 benchmark 结果夸大成公开通用数据集结论。随包 benchmark 覆盖检索、跨语言、敏感检测、遗忘、冲突、图谱、质量校验、真实风格 auditd、shell history 和工具结果，目的是证明赛题要求能力可复验。后续如果进入更大规模评测，可以继续扩展真实日志和用户行为样例。当前指标应理解为“在公开随包 benchmark 和 openKylin 证据包上的可复验结果”。

### 11.3 精准遗忘和普通删除有什么区别？

答：普通删除通常只删除数据库记录或隐藏搜索结果。MemGuardOS 的精准遗忘包含自然语言候选定位、dry-run 预览、用户确认、tombstone、FTS/图谱清理、段文件 compact 和明文泄漏探针验证。也就是说，我们关注的是“哪些该删”“删之前能否确认”“删完是否可证明”。

### 11.4 为什么用 mmap + SQLite，而不是直接上向量数据库？

答：赛题强调 Linux/openKylin 和端侧部署。mmap + SQLite 在 openKylin 上容易部署、资源占用低、可解释、可审计，也便于 compact 后做物理明文验证。向量数据库可以作为增强，但不是默认必要依赖。我们还提供 Kylin vector SDK 探针和 embedding 可选重排，为后续替换或融合系统 SDK 留出接口。

### 11.5 这个系统如何应用于智能体？

答：MemGuardOS 不直接限定某一个 Agent 框架，而是提供 Agent 所需的记忆服务。上游 Agent 可以通过 CLI 或 Unix socket API 写入工具结果、查询偏好、批量检索任务相关记忆、构建 RAG 上下文包，再交给本地或远程 LLM 生成回答。换句话说，它处在 Agent 的“记忆层”和“生成前上下文层”。

### 11.6 是否需要购买 LLM API？

答：不需要。MemGuardOS 默认不依赖外部 LLM API。它主要负责记忆提取、检索、脱敏、精准遗忘和上下文构建。生成回答可以由上游 Agent 选择本地模型或远程模型；如果不配置 provider，系统也能完成核心评测和演示。

### 11.7 BPF LSM 的意义是什么？

答：BPF LSM 用来证明系统可以从应用层安全治理扩展到内核安全钩子。我们在 openKylin 上验证了 `file_open` attach 和安全测试文件强制拒绝。当前默认只用于测试文件，避免影响系统登录或关键服务。它是安全增强路径，不是主功能的唯一依赖。

### 11.8 UKUI 插件的意义是什么？

答：UKUI/Peony 插件用于证明系统可以和 openKylin 桌面环境联动。当前 Peony 文件管理器右键入口采用“预览后确认”的产品流程：先扫描用户主动选择的文件，识别敏感风险和建议动作，生成带签名的 manifest；用户确认后才把安全文本以 `peony_file` 来源导入，目录、大文件、非文本文件和敏感文件不会被默认写入长期记忆。UKUI 控制中心提供服务、SDK、审计、cgroup、Polkit 和诊断导出操作，托盘提供状态提醒和快捷入口。这样桌面联动不是一个展示按钮，而是和记忆写入、敏感治理、审计链、服务治理形成闭环。

### 11.9 和普通 RAG 项目相比有什么优势？

答：普通 RAG 项目通常关注文档切片和向量召回。MemGuardOS 面向 OS Agent，除了检索，还覆盖多源系统行为、敏感治理、精准遗忘、审计哈希链、namespace 隔离、systemd/cgroup、auditd、BPF LSM 和 openKylin 证据。它更像一个本地记忆基础设施，而不是一个问答 demo。

### 11.10 后续可以怎么扩展？

答：后续可以扩展三条线：第一，引入更强的本地小模型或 Kylin SDK 作为默认语义抽取和向量检索后端；第二，完善 UKUI 可见安装和桌面交互；第三，扩展更大规模真实日志、真实命令历史和真实用户行为评测集。现有架构已经为这些增强预留接口。

## 12. 结束语

总结来说，MemGuardOS 做的是一套面向 Linux/openKylin OS Agent 的本地记忆基础设施。它覆盖多源记忆提取、偏好和知识建模、敏感治理、混合检索、RAG 上下文、精准遗忘、审计验证和操作系统机制集成。我们希望它回答的不只是“智能体能不能记住”，更是“它应该记住什么、能否安全使用、能否真正忘掉、能否在 openKylin 上被复验”。

## 13. 5 分钟压缩版讲稿

各位老师好，我们的作品是 MemGuardOS，对应赛题 3“面向 Linux 的智能体记忆提取与精准遗忘机制”。我们认为 OS Agent 的记忆问题不是普通聊天记录问题。Agent 在 Linux 桌面和开发环境中会长期接触用户偏好、命令历史、配置文件、工具结果、系统日志和潜在敏感凭据，因此系统必须解决四件事：从多源数据中提取有价值记忆，在生成前检索和脱敏，在用户要求时精准遗忘，并且能体现 openKylin/Linux 操作系统机制。

MemGuardOS 的架构分为多源接入、敏感治理、结构化记忆、轻量存储、混合检索、精准遗忘和 OS 集成几部分。输入来源包括文本、文件、结构化配置、shell history、工具执行结果、OS event、journald 和 auditd 日志。系统将输入抽取为偏好记忆、知识记忆和敏感策略记忆，并记录来源、类型、层级、实体、关系、版本、敏感标签和审计信息。

存储层采用 mmap 追加式段文件和 SQLite。正文写入段文件，元数据、FTS、版本、图谱和审计链写入 SQLite。检索层融合 FTS、稳定 hash-vector、图谱召回、跨语言技术词扩展和冲突解决，可以生成已脱敏、带 token 预算估算的 RAG 上下文包。默认主链路不依赖外部 LLM API、GPU 或重型向量数据库，适合 openKylin 端侧复验。

精准遗忘是项目重点。用户可以用自然语言提出遗忘请求，系统先 dry-run 展示候选，用户确认后写入 tombstone，清理 FTS 和图谱索引，执行 compact，并用探针验证段文件和元数据中是否仍存在目标明文。这个流程强调可确认、可审计、可证明，不只是从搜索结果中隐藏。

在 OS 机制方面，项目实现了 namespace 多会话隔离、systemd daemon、cgroup 资源限制、journald 桥接、auditd 事件接入、BPF LSM 安全测试文件强制拒绝、BPF JSON 策略生成、Peony 右键菜单可见验证，以及 UKUI 控制中心入口可见验证。同时提供 CLI、Unix socket API 和本地 Web 控制台。

当前 openKylin 证据显示：单元测试 294 passed，28 组真实 OpenHands 会话（含 8 组 holdout 留出盲测）中记忆系统层与 Agent 行为层均为 28/28；真实会话实际执行 `rg`，并由 Hook 拒绝 `rm -rf`、`reboot` 和 `sudo systemctl restart` 等高风险命令；10k 负载检索 P95 为 10.105 ms，P99 为 75.255 ms，RSS 为 130444 KB。我们会准确说明边界：小参数模型原生输出与 MemGuardOS 适配层恢复必须分开表达；精准遗忘只保证 MemGuardOS 管理的事件、记忆、索引、图谱和段文件边界；Kylin SDK 是可选增强，其首次推理存在高尾延迟，BPF LSM 默认只拦安全测试文件。

总结来说，MemGuardOS 的核心价值是把智能体记忆、精准遗忘和 Linux/openKylin 操作系统机制结合起来，形成一套可运行、可测试、可审计、可扩展的 OS Agent 记忆基础设施。谢谢各位老师。
