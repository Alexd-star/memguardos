# 极致补强路线与风险决策

本文回答三个问题：

1. 当前不能夸大的能力，是否能通过继续查资料和开发补足？
2. 如果要在性能和稳定性不下降的前提下继续冲高分，应优先补什么？
3. Kylin embedding SDK 推理超时到底卡在哪里？

## 1. 总体结论

| 能力 | 是否建议当前补 | 原因 |
|---|---|---|
| UKUI 联动 | 建议补轻量版，已补通知 smoke | 低风险，不影响核心指标，可增强 openKylin 生态观感 |
| 外部 LLM 生成器 | 建议补适配层，不建议设为默认路径 | 可增强完整 Agent 链路，但不能依赖网络或付费模型通过比赛测试 |
| fanotify 事件生产者 | 可选补 | 比 eBPF/LSM 风险低，但需要 root/权限和更多测试 |
| eBPF/LSM 内核钩子 | 不建议当前硬上主路径 | 内核配置、权限、加载方式和 openKylin 兼容性风险高，容易破坏稳定提交 |
| Kylin embedding 主检索 | 暂不替换默认路径 | 当前 SDK 可检测、模型可见，但真实推理超时；默认 FTS/hash 路径指标稳定 |

当前最优策略是：**主路径保持稳定，低风险增强补证据，高风险内核项作为后续增强，不牺牲已达标性能和 openKylin 可复现性。**

## 2. 权威资料依据

### 2.1 eBPF/LSM

Linux 内核文档说明 BPF LSM 程序可以挂到 LSM hook 上，但这类能力依赖内核 BPF/LSM 支持、BTF、加载权限和 verifier 约束。它适合作为高阶增强，不适合作为比赛后期才加入的默认主路径。

参考：

- Linux Kernel BPF LSM 文档：<https://docs.kernel.org/bpf/prog_lsm.html>
- Linux Kernel BPF 文档入口：<https://docs.kernel.org/bpf/>

决策：

- 不夸大“已实现 eBPF/LSM 内核级拦截”。
- 当前用 auditd 真实审计事件满足“结合 OS 级机制，不停留于应用层正则”。
- 已补独立可选脚本 `scripts/bpftrace_sensitive_open.bt` 和 `scripts/run_bpftrace_sensitive_probe.sh`，不接入默认测试链路；只有环境具备 bpftrace、root 权限和内核 tracepoint 支持时才启用。

### 2.2 fanotify

fanotify 是 Linux 文件访问通知/权限事件机制，适合监控敏感路径访问。相比 eBPF/LSM，它更容易做成用户态增强，但仍需要 Linux 权限、挂载点/路径标记和 openKylin 实测。

参考：

- Linux fanotify 文档：<https://docs.kernel.org/filesystems/fsnotify.html>
- man7 fanotify：<https://man7.org/linux/man-pages/man7/fanotify.7.html>
- man2 fanotify_init：<https://man7.org/linux/man-pages/man2/fanotify_init.2.html>
- man2 fanotify_mark：<https://man7.org/linux/man-pages/man2/fanotify_mark.2.html>

决策：

- fanotify 可作为 auditd 的补充事件生产者。
- 若实现，应放在可选脚本中，不替代 auditd 主证据。

### 2.3 UKUI 桌面通知

openKylin/UKUI 通知守护进程遵循 freedesktop 桌面通知生态，`notify-send` 是低风险、可复现的桌面联动方式。

参考：

- freedesktop Desktop Notifications Specification：<https://specifications.freedesktop.org/notification-spec/latest/>
- openKylin UKUI notification daemon 仓库：<https://gitee.com/openkylin/ukui-notification-daemon>

当前已补：

- `scripts/ukui_notify_smoke.sh`
- `docs/UKUI轻量联动说明.md`

诚实表述：

- 可以说“已实现 UKUI/freedesktop 桌面通知轻量联动”。
- 不能说“已实现 UKUI 深度插件、Peony 右键菜单、控制中心插件”。

### 2.4 外部 LLM 生成器

外部 LLM 生成器可以补成 provider-agnostic 适配层：输入 MemGuardOS 的 `build-context` 输出，交给本地模型或远程模型生成回答。但比赛核心不应依赖它，因为网络、API Key、费用、模型版本都会影响复现。

决策：

- 当前已实现“RAG 生成前上下文包”和 provider-neutral prompt 渲染，满足记忆调用链。
- 若要补外部 LLM API 调用，建议只做可选 adapter，默认关闭。
- 文档表述为“可接入外部 LLM 的上下文构建链路”，不说“内置完整生成模型”。

## 3. Kylin embedding SDK 超时诊断

### 3.1 已确认可用的部分

openKylin VM 中已检测到：

- 动态库：`libkysdk-coreai-embedding.so.1`
- 头文件：`/usr/include/kylin-ai/coreai/embedding/embedding.h`
- 模型信息：`dim=768`，`name=ensemble-embd_gte-base_uint8-text`，`ondevice=true`
- vector SDK：`libkysdk-vector-engine-client.so.1`
- vector engine 用户服务：`kylin-ai-vector-engine.service active`
- vector socket：`/tmp/kylin-ai-vector-engine-1000.sock`
- Kylin vector SDK C++ 探针：建表、插入、搜索、清理成功

### 3.2 超时发生的位置

超时不是发生在库加载或模型信息读取阶段，而是发生在真实文本向量推理阶段：

```text
text_embedding(session, text, &result)
```

历史证据中 SDK 返回：

```json
{
  "ok": false,
  "error_code": 3,
  "error_message": "Timeout was reached",
  "length": 0
}
```

本轮复查时，外层 `timeout 35` 只看到：

```text
Proxy init engine sessionId:...
Proxy init engine sessionId:...
```

随后进程没有在 35 秒内正常返回，说明推理链路可能卡在 SDK 代理、DBus、runtime engine 或 on-device embedding engine 调度上。

### 3.3 已排除的低级错误

根据 `/usr/include/kylin-ai/coreai/embedding/embedding.h`：

- `text_embedding_create_session()` 返回 `TextEmbeddingSession *`
- `text_embedding_init_session(session)` 返回 `int`
- `text_embedding_get_model_info(session, char **model_info)` 返回 `bool`
- `text_embedding(session, const char *text, EmbeddingResult **result)` 返回 `bool`
- `embedding_result_destroy(EmbeddingResult **result)` 销毁同步结果

当前 ctypes 签名与头文件基本一致，因此更像运行时/服务侧超时，而不是简单函数签名错误。

### 3.4 可能原因

| 可能原因 | 证据 | 后续排查 |
|---|---|---|
| on-device embedding engine 首次加载模型慢或阻塞 | 只打印 Proxy init engine，不返回向量 | 单独 C++ 最小探针验证同步/异步接口 |
| DBus 会话或 runtime 调度超时 | 历史错误明确为 `Dbus-close:aisdk_text Timeout was reached` | 查看 Kylin AI runtime/user journal |
| VM 资源或图形会话状态影响 | VM CPU/内存有限，进程可高 CPU 等待 | 增加内存/CPU、关闭低功耗冻结策略后复测 |
| SDK 包版本问题 | 当前包版本固定在 openKylin 2.0 SP2 | 查询官方 issue 或升级包后复测 |

### 3.5 当前工程决策

- 不把 Kylin embedding 放入默认检索主路径。
- 保留 `sdk-status --probe-embedding` 作为真实探测命令。
- 默认使用 SQLite FTS + 稳定 hash-vector + 图谱扩展，保证 10k P95 < 500 ms。
- vector SDK 已有真实 C++ 搜索探针，可作为 openKylin SDK 适配证据。

## 4. 性能与指标极致路线

### 4.1 不破坏稳定性的优先级

1. **扩大 benchmark 难例**：增加同义、近义、跨语言、干扰项、误删边界样例。
2. **固定随机性与数据规模**：所有评测使用固定 seed、固定 latency-size、固定 query 数。
3. **继续保留默认轻量检索**：避免把不稳定 SDK 推理放进主指标路径。
4. **增加可选增强，不进默认链路**：UKUI、fanotify、LLM adapter 都应默认关闭或脚本化。
5. **最终 openKylin 复跑**：所有最终指标以 openKylin VM 证据包为准。

### 4.2 可继续冲高分的实现项

| 优先级 | 项目 | 价值 | 风险 |
|---|---|---|---|
| P0 | 录制 openKylin 演示视频 | 交付硬要求 | 低 |
| P0 | 最终证据包复跑 | 防止指标过期 | 低 |
| P1 | 扩充 benchmark 到更难样例 | 提升指标可信度 | 中 |
| P1 | 可选 LLM adapter | 展示 Agent 完整链路 | 中 |
| P1 | fanotify 可选生产者 | OS 深度增强 | 中 |
| P2 | Peony/UKUI 插件 | openKylin 生态亮点 | 中高 |
| P3 | eBPF/LSM 内核拦截 | 已有 bpftrace 可选探针脚本；若要做强制拦截仍属高风险 | 高 |
| P3 | Kylin embedding 主路径 | SDK 原生亮点 | 高，当前超时未解 |

## 5. 答辩建议话术

推荐说法：

> 当前 MemGuardOS 的默认链路采用 SQLite FTS、稳定 hash-vector、图谱扩展和 auditd/systemd/cgroup 等 Linux 原生机制，保证 openKylin 上稳定运行和指标可复现。对于 Kylin embedding SDK、eBPF/LSM、UKUI 深度插件等高风险或鼓励项，我们做了真实探测和低风险增强；eBPF 侧提供 bpftrace 可选探针，但不在未稳定前夸大为主路径能力。

不推荐说法：

- “已经完整实现 eBPF/LSM 拦截。”
- “已经用 Kylin embedding SDK 做主检索。”
- “已经实现 UKUI 深度插件。”
- “已经内置完整外部 LLM 生成器。”
