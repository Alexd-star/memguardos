# MemGuardOS 的 OS 机制

MemGuardOS 面向 Linux/openKylin 智能体记忆场景，不只是应用层 RAG 存储。本文列出当前已实现或已验证的 OS 相关机制。

## 1. 基于 mmap 的版本化段文件

实现文件：

- `memguard/store/mmap_store.py`

行为：

- 记忆记录存储为追加式 JSONL 段文件。
- 读取时使用 Python `mmap`，将段文件映射到进程地址空间。
- 更新不会覆盖旧 payload，而是追加新版本。
- 遗忘先追加 tombstone。
- `compact` 只保留存活记录，从段文件中移除已遗忘明文。

证据命令：

```bash
python -m memguard.cli.memctl ingest --text "temporary project codename blue-river"
python -m memguard.cli.memctl forget "忘掉 temporary project codename" --yes
python -m memguard.cli.memctl compact
python -m memguard.cli.memctl verify-forget <memory_id> --probe "temporary project codename blue-river"
```

测试证据：

- `test_forget_compact_removes_plaintext_from_segment`

## 2. namespace 多会话隔离

实现文件：

- `memguard/config.py`
- `memguard/service.py`
- `memguard/cli/memctl.py`
- `scripts/memguardd@.service`

行为：

- 默认 namespace 为 `default`，继续使用 `~/.memguardos/memory.segment`、`~/.memguardos/memguard.sqlite3` 和 `~/.memguardos/sensitive_patterns.json`，兼容旧数据。
- 显式 namespace 使用 `~/.memguardos/namespaces/<name>/` 下的独立 mmap 段文件、独立 SQLite 元数据库和独立自定义敏感规则文件。
- namespace 名只允许 1-64 位 ASCII 字母、数字、点、下划线和横线，并禁止路径穿越、空格、斜杠和 Windows 保留设备名，避免把隔离目录解析到预期根目录之外。
- 记忆写入、检索、遗忘、审计、敏感规则均在当前 namespace 内完成，审计详情自动记录 `namespace` 字段。
- `memguardd@.service` 支持 systemd 模板实例，例如 `memguardd@demo-a.service` 和 `memguardd@demo-b.service`，每个实例使用不同 `MEMGUARD_NAMESPACE`、不同 Unix socket 和不同 systemd cgroup。

证据命令：

```bash
python -m memguard.cli.memctl --namespace alpha ingest --text "alpha 会话只保存 openKylin systemd MemoryMax 方案。"
python -m memguard.cli.memctl --namespace beta ingest --text "beta 会话只保存 auditd shadow access 方案。"
python -m memguard.cli.memctl --namespace alpha search MemoryMax
python -m memguard.cli.memctl --namespace beta search MemoryMax
python -m memguard.cli.memctl --namespace alpha namespace-status
python -m memguard.cli.memctl --namespace beta namespace-status
python -m memguard.cli.memctl namespaces
```

systemd 模板服务证据命令：

```bash
sudo bash scripts/install_openkylin.sh "$(pwd)"
sudo systemctl start memguardd@demo-a memguardd@demo-b
systemctl status memguardd@demo-a memguardd@demo-b
systemctl show memguardd@demo-a memguardd@demo-b -p ControlGroup -p MemoryMax -p CPUQuotaPerSecUSec
MEMGUARD_NAMESPACE=demo-a python -m memguard.cli.memctl namespace-status
MEMGUARD_NAMESPACE=demo-b python -m memguard.cli.memctl namespace-status
```

测试证据：

- `test_namespace_paths_are_safe_and_default_is_backward_compatible`
- `test_namespace_isolation_keeps_records_patterns_and_audit_separate`
- openKylin 证据：`docs/evidence/latest/namespace_isolation.txt` 中 `beta search MemoryMax` 返回空列表，证明 alpha/beta 记忆未串库。

## 3. systemd/cgroup 资源控制

实现文件：

- `scripts/memguardd.service`
- `scripts/memguardd@.service`
- `scripts/install_openkylin.sh`
- `memguard/os_guard/cgroup.py`

行为：

- 服务文件设置：
  - `MemoryMax=512M`
  - `CPUQuota=50%`
- 模板服务 `memguardd@.service` 为每个 namespace 实例提供独立 systemd service 和 cgroup。
- `memctl doctor` 和 `memctl status` 在 Linux/openKylin 上报告 cgroup v2 状态。

openKylin 证据命令：

```bash
sudo bash scripts/install_openkylin.sh "$(pwd)"
sudo systemctl start memguardd
systemctl status memguardd
python -m memguard.cli.memctl status
systemctl show memguardd -p MemoryMax -p CPUQuotaPerSecUSec
cat /sys/fs/cgroup/system.slice/memguardd.service/memory.max
cat /sys/fs/cgroup/system.slice/memguardd.service/cpu.max
```

模板服务证据：

- `docs/evidence/latest/systemd_namespace.txt`
- `memguardd@demo-a.service` 和 `memguardd@demo-b.service` 均为 `active (running)`。
- 两个实例的 `ControlGroup` 分别位于 `system-memguardd.slice` 下。
- 两个实例均显示 `MemoryMax=536870912`、`CPUQuotaPerSecUSec=500ms`，cgroup v2 文件中 `memory.max=536870912`、`cpu.max=50000 100000`。

## 4. 索引缓存、冷热分层与批量检索

实现文件：

- `memguard/retrieval/hybrid.py`
- `memguard/service.py`
- `memguard/store/sqlite_meta.py`
- `memguard/eval/run_eval.py`

行为：

- `mmap` 段文件依赖 Linux 页缓存承载顺序读取路径。
- SQLite FTS 先做候选预筛，`list_memories(..., limit=...)` 在 SQLite 侧限制候选数量，避免把全部记忆拉到应用层后再裁剪。
- token 切分和稳定 hash-vector 计算使用 LRU 缓存，减少重复查询和重复候选文本的 CPU 开销。
- `working`、`session`、`long_term` 三层用于冷热数据分层：短期 working 优先淘汰，session 可在任务结束后批量清理，long_term 参与稳定 RAG 复用。
- `memory-policy` 汇总三层数量、来源分布、敏感等级分布、mmap/SQLite 占用、旧版本/墓碑数量、可淘汰候选、compact 建议和 cgroup 状态。
- `batch-search` 面向 OS Agent 的任务规划、工具调用、结果生成多查询场景。每个 worker 使用独立服务实例和 SQLite 连接执行只读检索，结果按输入顺序合并，整批请求写入一次 `batch_search` 审计事件，避免逐条子查询写审计造成读路径写放大。

证据命令：

```bash
python -m memguard.cli.memctl memory-policy --eviction-limit 10
python -m memguard.cli.memctl batch-search \
  "任务规划 systemd cgroup" \
  "工具调用 pytest journalctl" \
  "结果生成 运维报告 证据" \
  --top-k 3 \
  --workers 3
python -m memguard.eval.run_eval --latency-size 1000 --latency-queries 120
```

本地最新评测结果：

- 1k 负载 P95：`0.611 ms`。
- 6 worker 并发检索 P95：`121.101 ms`。
- Agent 批量检索 P95：`3.580 ms`。
- 记忆分层策略报告：通过。
- RAG token 预算与脱敏保持：通过。

边界：

- 当前没有把所有读写路径改为 Linux AIO 或 io_uring；已实现的是赛题鼓励项中更稳妥、可复现的索引预筛、缓存、冷热分层、批量并发检索、本地 Unix socket 数据传输和 systemd/cgroup 资源调度。

## 5. journald 审计桥接

实现文件：

- `memguard/os_guard/journald.py`
- `memguard/store/sqlite_meta.py`

行为：

- 每个关键事件都会写入 SQLite 审计表。
- 在 systemd 系统上，事件通过 `systemd-cat` 镜像到 journald。
- 审计行通过 `prev_hash` 和 `event_hash` 串联。
- `verify-audit` 验证哈希链。

证据命令：

```bash
python -m memguard.cli.memctl verify-audit
journalctl -t memguardd -n 50
```

测试证据：

- `test_audit_hash_chain_verification`
- `test_concurrent_audit_writes_preserve_hash_chain`
- openKylin 证据：`docs/evidence/latest/audit_concurrency.txt` 中 6 线程共 72 条事件写入后 `verify.ok=true`。

## 6. OS 事件接入层

实现文件：

- `memguard/os_guard/events.py`
- `memctl ingest-os-event`

行为：

- 接受 JSON 事件或 audit/fanotify 风格日志。
- 抽取路径、进程、动作和事件类型。
- 路径作为 OS 上下文进入敏感检测器。
- `.ssh/id_rsa`、`.env`、`/etc/shadow` 等路径会被视为高风险来源。

证据命令：

```bash
python -m memguard.cli.memctl ingest-os-event --json '{"event_type":"fanotify_open","path":"/home/u/.ssh/id_rsa","process":"cat","action":"read"}'
```

测试证据：

- `test_os_event_sensitive_path_is_blocked`

## 7. auditd 规则与真实日志接入

实现文件：

- `memguard/os_guard/auditd.py`
- `memguard/os_guard/auditd_events.py`
- `scripts/install_auditd_rules.sh`
- `scripts/auditd_to_memguard.sh`

行为：

- `memctl auditd-rules --format auditctl` 输出即时 `auditctl` 命令。
- `memctl auditd-rules --format rules-file` 输出 `/etc/audit/rules.d` 兼容规则。
- `scripts/install_auditd_rules.sh` 安装规则并重载 auditd。
- `scripts/auditd_to_memguard.sh` 将 `ausearch` 结果转换为 MemGuardOS OS 事件。

证据命令：

```bash
python -m memguard.cli.memctl auditd-rules --format auditctl
sudo bash scripts/install_auditd_rules.sh "$(pwd)"
sudo ausearch -k memguard_sensitive -i
bash scripts/auditd_to_memguard.sh "$(pwd)" memguard_sensitive 200 --summary
```

测试证据：

- `test_auditd_rule_generation`
- 真实 `/etc/shadow` 访问日志在 openKylin 上被解析并阻断。

## 8. BPF LSM 强制拦截增强

实现文件：

- `native/bpf_lsm/memguard_lsm.bpf.c`
- `native/bpf_lsm/memguard_lsm_loader.c`
- `native/bpf_lsm/memguard_lsm_policy.h`
- `native/bpf_lsm/Makefile`
- `scripts/generate_bpf_lsm_policy.py`
- `scripts/run_bpf_lsm_enforcer.sh`

行为：

- 在支持 BPF LSM 的 Linux/openKylin 内核上，将 eBPF 程序挂载到 `lsm/file_open`。
- 默认演示模式只对 `/tmp/memguardos_lsm_secret` 返回 `-EACCES`，避免影响登录、SSH、sudo 或 PAM。
- 生产 denylist 通过 `MEMGUARDOS_PRODUCTION_DENYLIST` 编译开关保留，可扩展到 SSH 私钥、AWS/Kubernetes 凭据、`.env`、`/secrets/`、`service_account` 等高风险路径。
- `scripts/generate_bpf_lsm_policy.py` 可从 JSON 策略生成静态 `memguard_lsm_policy.h`，策略只接受安全的绝对路径片段，便于在隔离测试机上进行代码审查后再编译加载。
- loader 运行期间保持 BPF link；停止 loader 后自动释放。
- 该增强要求 root、BTF、clang、libbpf 开发头，并且 `/sys/kernel/security/lsm` 中包含 `bpf`。

证据命令：

```bash
bash scripts/run_bpf_lsm_enforcer.sh docs/evidence/latest
python3 scripts/generate_bpf_lsm_policy.py --policy data/demo/bpf_lsm_policy.json --output /tmp/memguard_lsm_policy.generated.h
```

openKylin 实测结果：

- `scripts/run_bpf_lsm_enforcer.sh` 在 openKylin 6.6.0-19 上完成编译、attach。
- `/sys/kernel/security/lsm` 包含 `bpf`，BTF 可读。
- 访问 `/tmp/memguardos_lsm_secret` 返回 `Permission denied`，证据为 `enforcement_result=denied`。

边界：

- 默认稳定主路径仍是 auditd 真实审计 + MemGuardOS 高风险写入阻断。
- BPF LSM 属于可选强制拦截增强；默认安全测试路径不覆盖 `/etc/shadow`，避免影响系统登录链路。

## 9. UKUI 深度联动增强

完整实现细节见 `docs/Peony与UKUI桌面集成实现说明.md`。本节只列出 OS 机制视角下的核心行为和证据。

实现文件：

- `native/ukui/peony-memguard/`
- `native/ukui/ukcc-memguard/`
- `scripts/build_ukui_plugins.sh`
- `scripts/probe_ukui_deep_plugins.sh`
- `scripts/verify_ukui_plugins.sh`

行为：

- Peony 右键菜单插件通过 `Peony::MenuPluginInterface` 增加“发送到 MemGuardOS 记忆安全扫描”动作，把选中文件路径转为统一 OS event。
- UKUI 控制中心插件通过 `CommonInterface` 提供 MemGuardOS 记忆安全入口，面向本机管理员提供运行环境检查、审计链校验、端侧向量能力检查、诊断报告和本地控制台入口。底层分别调用 `doctor`、`verify-audit`、`sdk-status --probe-embedding`、`diagnostics --probe-sdk` 和 `web` 命令。
- 插件要求 `libpeony-dev`、`libukcc-dev` 和 Qt5 开发工具。

证据命令：

```bash
bash scripts/probe_ukui_deep_plugins.sh docs/evidence/latest
bash scripts/build_ukui_plugins.sh
bash scripts/verify_ukui_plugins.sh
```

边界：

- 当前默认演示仍可使用 `ukui_notify_smoke.sh` 展示轻量桌面联动。
- Peony/UKCC 插件是 openKylin 生态增强项；当前已在 openKylin 安装开发包后真实构建出两个 `.so`。openKylin ostree/overlay 只读 `/usr` 场景已通过 bind mount 演示安装处理，Peony 右键菜单项“发送到 MemGuardOS 记忆安全扫描”已在桌面右键菜单中可见验证，UKUI 控制中心入口“MemGuardOS 记忆安全”已在设置界面中可见验证。当前源码进一步提供本机运维面板，覆盖运行环境检查、审计链校验、端侧向量能力检查、诊断报告和本地控制台入口。

## 10. Linux-only 扩展接口

当前 OS 事件层已经支持 auditd 驱动接入、BPF LSM 可选强制拦截原型和便携 JSON shim。其他 Linux-only 事件生产者可以按同一接口扩展，例如：

1. fanotify 监听敏感目录。
2. 将 Peony 插件安装流程做成 `.deb` 包。

这些生产者应继续输出统一的 `ingest-os-event` 格式，从而保持记忆和安全逻辑不变。
