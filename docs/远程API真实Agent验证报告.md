# MemGuardOS 远程 API 真实 Agent 验证报告

日期：2026-07-08

本文记录本轮在 openKylin 虚拟机中使用远程 OpenAI 兼容模型 API 验证 OpenHands 与 MemGuardOS 真实闭环的结果。该验证的目的不是证明虚拟机可以流畅运行大模型，也不是证明模型原生能力达到满分，而是验证在更贴近实际产品部署的条件下，MemGuardOS 能否稳定完成用户与 Agent 交互记忆的采集、复用、约束和遗忘。

## 1. 为什么要做这轮验证

openKylin 虚拟机可以运行 MemGuardOS、OpenHands SDK、终端工具和桌面组件，但本地小模型对 CPU、内存和模型服务稳定性要求较高。若强行把模型推理也放在虚拟机内，演示容易被模型冷启动、显存不足、CPU 推理慢和网络依赖拖累，反而不能清楚展示记忆系统本身的价值。因此本轮采用“本机执行 Agent 与记忆治理，远程 API 提供模型推理”的方式。

这种方式在工程上是合理的：OpenHands 仍在 openKylin 中创建会话、调用工具、接收用户消息和产出事件；MemGuardOS 仍在本机完成记忆抽取、上下文构建、策略拦截、精准遗忘和审计；远程 API 只承担语言模型推理。这样可以把“模型算力问题”和“记忆系统能力问题”分开验证。

远程 API 密钥只通过临时环境变量传入，未写入代码、文档和证据文件。

## 3. 本轮发现并修正的问题

本轮验证有实际工程价值，因为它不是只跑一个已经知道会通过的脚本，而是在真实 OpenHands 运行中暴露了多处集成问题：

1. 虚拟机缺少 `tmux`，OpenHands 终端会话稳定性不足。本轮已在 openKylin 中安装并验证。
2. 虚拟机缺少 `rg`，与“代码搜索优先使用 rg”的用户习惯不匹配。本轮已安装 `ripgrep` 并验证。
3. 宿主机 VPN 只监听 Windows 回环地址，虚拟机不能直接访问。本轮改用同 SSH 会话的反向端口转发，避免后台隧道在重启后失效。
4. 远程 API 与 OpenHands/LiteLLM 的 Responses API 行为存在兼容差异。本轮增加 `OPENHANDS_LITELLM_STORE=true` 支持，并允许用 `OPENHANDS_MODEL_CANONICAL_NAME` 进行能力识别兼容。
5. 小模型有时用自然语言表达“应该使用 rg”，但没有生成 OpenHands 原生工具调用。本轮增加安全的自然语言搜索意图恢复，只允许 `rg/grep` 的只读搜索，不允许 shell 元字符、绝对路径和危险参数。
6. 高风险操作有时表现为自然语言承诺或拒绝，而不是工具调用事件。本轮增加直接用户请求的高风险识别与可见阻断事件，使“需要确认”的安全策略能被审计和展示。

这些修改提高的是“MemGuardOS + OpenHands 适配器”的可靠性，而不是修改模型权重。所有恢复和阻断都会留下来源标记，不能冒充模型原生能力。

## 5. 该结果能证明什么

本轮结果可以证明：在 openKylin 虚拟机中，OpenHands 可以接入远程模型 API，MemGuardOS 可以在真实 Agent 会话中采集用户消息、工具调用、工具结果和安全策略事件，并把记忆用于后续工具选择、输出约束、风险阻断和遗忘验证。

它还证明了系统在真实集成环境中处理了模型服务兼容、终端工具缺失、网络代理、自然语言工具意图和高风险请求可审计阻断等问题。这些问题正是企业级产品落地时会遇到的工程问题，因此本轮验证对项目质量有实质帮助。

## 6. 该结果不能证明什么

本轮 20/20 通过不能被解释为“任意 OpenHands 任务都能 100% 完成”。它只说明当前 20 组受控场景在指定模型、指定 API、指定 OpenHands 版本和当前 MemGuardOS 适配层下通过。远程模型的推理质量、API 可用性和网络稳定性仍是外部依赖。

同时，适配器中的自然语言意图恢复和高风险阻断是 MemGuardOS 产品能力的一部分，不是模型原生能力。答辩中应明确说明：项目评价对象是记忆系统和 Agent 接入闭环，不是单独评测大模型。

## 7. 后续建议

最终提交前，建议保留两套口径：一套是本地小模型或确定性实验，证明系统不依赖云端 API 也能复验核心逻辑；另一套是远程 API 演示，展示真实 OpenHands 使用时更流畅、更接近产品的体验。两套证据共同说明项目既可复现，又具备实际演示质量。
