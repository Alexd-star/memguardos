# MemGuardOS 架构决策记录

日期：2026-05-18

本文记录当前实现背后的关键技术取舍，用于答辩、复盘和后续开发约束。每一项决策都要符合“需求匹配 -> 最佳实践核查 -> 决策记录 -> 实现 -> 验证 -> 规划更新”的闭环。

## ADR-001：FTS 候选预筛选 + 混合重排

**决策：** 检索链路先使用 SQLite FTS 做候选预筛选，再合并图谱候选和少量最近记忆，最后进入混合重排。

**原因：** 全量表混合打分实现简单，但不适合端侧规模化记忆检索。此前 openKylin 上 5k 记忆压测曾超过 500 ms P95 目标；改为 FTS 预筛选后，10k 记忆验证仍低于 500 ms P95。

**备选方案：**

- 全量打分：实现最简单，但延迟随记忆规模增长过快。
- 完全依赖外部向量库：语义检索能力更强，但端侧离线部署更重，也更难稳定控制资源。
- FTS 预筛选 + 混合重排：保留本地、轻量、可解释、低延迟的基础路径，因此作为默认方案。

**验证证据：** openKylin 上执行 `python -m memguard.eval.run_eval --latency-size 10000 --latency-queries 150`，优化后负载 P95 低于 500 ms。

**补充优化：** 混合检索的轻量向量不再使用 Python 内置 `hash()`，因为它会受到进程随机种子的影响。当前改为 SHA-256 稳定哈希，保证不同进程、不同平台上的候选排序更可复现。

## ADR-002：麒麟文本向量化 SDK 先做可选探测，不强行进入主路径

**决策：** 检测 openKylin/麒麟文本向量化 SDK，并提供探测后端；默认检索仍保留稳定的哈希向量 + 词法回退路径。

**原因：** 虚拟机中能够检测到 `libkysdk-coreai-embedding.so.1` 和 768 维端侧文本模型，但真实推理目前在验证环境中超时。若强制把不稳定 SDK 调用放入主检索链路，会降低系统可靠性和演示可重复性。

**备选方案：**

- 只凭库检测就宣称完成 SDK 集成：证据不足，容易被质疑。
- 把 SDK 设为强依赖：当前超时会导致功能不稳定。
- SDK 可选探测 + 稳定回退：既诚实展示 openKylin 适配，又保证比赛演示和评测稳定。

**验证证据：** `python -m memguard.cli.memctl sdk-status --probe-embedding` 能返回模型元数据，但推理超时；相关限制已在 SDK 文档中明确说明。

## ADR-003：麒麟向量数据库 SDK 先用真实 C++ 探针验证

**决策：** 先用最小 C++ 探针验证麒麟向量数据库 SDK，再决定是否继续构建 Python 桥接层。

**原因：** 向量数据库 SDK 是原生服务型接口。C++ 探针直接覆盖创建集合、插入向量、加载、搜索、删除集合，比单纯检查动态库更能证明 SDK 路径真实可用。Python 桥接可以后续补充，但不应在 API 边界未完全稳定前成为主路径。

**备选方案：**

- 先写 Python `ctypes` 封装：接入应用更快，但 API 风险更高。
- 只做库检测：证据太弱。
- C++ 探针优先：最贴近 SDK 边界，也便于评审复现，因此采用。

**验证证据：** openKylin 上执行 `bash scripts/run_kylin_vector_probe.sh`，完成向量插入与近邻搜索，并返回命中结果。

## ADR-004：auditd 作为首选真实 OS 事件生产者

**决策：** 以 auditd 作为第一阶段真实敏感访问事件生产者，fanotify/eBPF 作为可选增强项。

**原因：** auditd 成熟、可脚本化、符合 Linux 安全审计实践，能够监控 `/etc/shadow`、SSH 密钥、配置目录等敏感路径。它能提供足够强的 OS 原生证据，同时避免内核模块、BPF 验证器、权限配置带来的额外风险。

**备选方案：**

- fanotify 优先：适合文件访问监控，但实现和权限处理更复杂。
- eBPF 优先：展示效果强，但比赛周期内搭建风险较高。
- auditd 优先：稳定、原生、已在 openKylin 验证，因此采用。

**验证证据：** openKylin 中真实访问 `/etc/shadow` 后产生 audit 日志，`scripts/auditd_to_memguard.sh` 能解析该日志，MemGuardOS 将其按敏感记忆阻断。

## ADR-005：基准评测必须包含困难样例和基线对比

**决策：** 使用显式 JSONL 基准集，并报告 text-only、无图谱混合检索、完整 MemGuardOS 三类对比。

**原因：** 面向国家级奖项的项目不能只靠演示，需要证明相对简单基线的增益。当前评测覆盖检索、跨语言、敏感检测、精准遗忘困难负例、冲突解决、图谱检索、记忆层级、延迟和资源指标。

**备选方案：**

- 只做演示验证：主观性强，不足以支撑答辩。
- 只报一个总分：不利于定位退化。
- 拆分指标并加入基线：最贴合赛题得分点，也方便后续优化。

**验证证据：** `python -m pytest -q` 和 `python -m memguard.eval.run_eval` 均覆盖评测行为。

## ADR-006：systemd/cgroup 作为部署与资源控制平面

**决策：** 守护进程部署围绕 systemd 服务、MemoryMax、CPUQuota 和 cgroup 证据构建。

**原因：** 赛题是操作系统方向。systemd/cgroup 证据能够证明 MemGuardOS 不是普通脚本，而是能被 openKylin 以系统服务方式约束和管理的组件。

**备选方案：**

- 只提供 CLI 演示：OS 集成证据不足。
- 只用 Docker 部署：可移植性好，但 openKylin 原生性弱。
- systemd/cgroup：评审可直接检查资源限制，因此采用。

**验证证据：** openKylin 验证已确认 `MemoryMax`、`CPUQuota`、`memory.max` 和 `cpu.max`。

## ADR-007：轻量化本地存储保持默认路径

**决策：** 默认采用 append-only mmap JSONL 段文件 + SQLite 元数据/FTS 的本地存储结构。

**原因：** 赛题鼓励端侧部署和轻量化存储。当前设计同时具备可审计追加历史、不可逆压缩清除、快速本地元数据查询，以及简单的备份和调试能力，不依赖常驻外部服务。

**备选方案：**

- 全部放入 SQLite：实现简单，但 mmap 和追加式 OS 机制证据较弱。
- 全部放入向量数据库：语义检索叙事更强，但更重，离线稳定性较差。
- mmap 段文件 + SQLite 元数据：在 OS 机制、可靠性和延迟之间平衡最好，因此采用。

**验证证据：** 评测报告会记录延迟、tracemalloc、进程 RSS 与存储占用。
