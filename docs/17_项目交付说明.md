# 17 项目交付说明

本文档说明 MemGuardOS 当前交付物、正式提交包边界、完整仓库包用途和最终提交前检查流程。更详细的竞赛提交口径见 [正式提交材料说明.md](正式提交材料说明.md) 和 [最终提交说明.md](最终提交说明.md)。

## 1. 交付物组成

当前项目交付物包括作品源码、运行脚本、原生增强源码、测试代码、benchmark 数据、中文正式文档、企业级操作手册、openKylin 证据包、评测报告、答辩材料和打包产物。代码、文档和证据共同构成作品可信度，不能只提交源码而缺少复验证据。

## 2. 正式竞赛提交包

正式提交包由 `scripts/package_submission.py` 生成，文件名形如：

```text
dist/memguardos_competition_submission_<时间戳>.zip
```

该包应包含 `memguard/`、正式运行脚本、`native/`、`tests/`、`data/`、`pyproject.toml`、`LICENSE`、正式中文文档、评测报告和 `docs/evidence/latest/`。它不应包含 Git 历史、CI 配置、缓存、虚拟环境、个人笔记、研究源材料或仅用于工程自检的脚本。

## 3. 完整工程仓库包

完整仓库包由同一脚本生成，文件名形如：

```text
dist/memguardos_full_repository_<时间戳>.zip
```

该包用于 GitHub Release、备份和后续维护，包含正式材料之外的工程支撑文件，如 `.github/`、`.devcontainer/`、贡献指南、更新日志、自检脚本、打包脚本和研究资料。

## 4. 交付前检查

正式提交前建议执行：

```bash
python scripts/release_preflight.py
python scripts/package_submission.py
python scripts/inspect_submission_package.py
python scripts/smoke_submission_archive.py
```

若 openKylin 证据已经过期，应先重新运行 openKylin 证据采集。若修改了文档，应重新运行链接检查。若修改了打包边界，应重新运行打包测试和提交包审计。

## 5. 人工确认项

最终提交仍需要人工确认三件事。第一，竞赛平台要求的压缩包命名、大小限制和提交字段是否与当前包匹配。第二，演示视频是否录制并能清晰展示 openKylin 运行、Web/UKUI 可见入口、精准遗忘和证据目录。第三，答辩时是否准确说明边界：默认抽取是可解释规则，Kylin SDK 是可选增强，BPF LSM 是安全测试路径，Web 控制台是本地控制台。

## 6. 维护建议

每次交付后应保留提交包、manifest、证据包和对应 Git commit。若后续继续开发，应避免直接修改历史证据；应重新采集新证据并更新 `docs/evidence/latest/`。文档更新时要同步检查 README、PROJECT_INDEX、编号文档和正式评审文档之间是否存在口径冲突。
