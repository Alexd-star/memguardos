# MemGuardOS 下一步开发补强规划

本文档用于记录 2026-07-01 之后的后续补强路线。目标不是继续堆叠展示性功能，而是围绕赛题硬要求、真实 Agent 闭环、openKylin 证据、企业级交付可信度和答辩可解释性，确定哪些事项必须补、哪些事项值得补、哪些事项不应过度投入。

## 1. 当前结论

截至当前分支，MemGuardOS 已经形成一套面向 openKylin 的智能体记忆提取与精准遗忘系统。核心能力覆盖用户-Agent 交互采集、偏好与知识抽取、状态-动作-结果程序性记忆、三阶段 RAG 上下文构建、范围化精准遗忘、审计链、systemd/namespace/cgroup/auditd/BPF LSM/UKUI/Peony 等操作系统集成、OpenHands 真实 Agent 适配和可复现评测。

从赛题要求角度看，当前不存在明确未实现的 P0 功能项。后续重点已经从“补主功能”转向“消除证据口径不一致、提高企业级可信度、扩大独立验证、降低评委质疑空间”。这类工作不会显著改变核心架构，但会直接影响最终材料的可信度、观感和抗追问能力。

## 2. 外部资料核对要点

OpenHands 官方文档把事件系统描述为不可变、类型化、追加式事件日志，并说明事件日志既驱动 Agent 执行，也可作为状态和集成点。MemGuardOS 采用 OpenHands 事件、工具调用、Hook 拒绝和上下文注入作为真实 Agent 接入边界，方向与 OpenHands 官方事件流模型一致。

OpenHands Hook 文档说明 Hook 可在会话关键时刻运行脚本，常见场景包括工具调用前后的控制。MemGuardOS 的高风险命令阻断、记忆注入和行为证据采集应继续以 Hook/runner/adapter 的组合形式表达，不能把适配层恢复能力夸大为小模型原生能力。

NIST SSDF 与 CISA 软件安全自证明材料强调安全开发、供应链可追溯、依赖清单、构建产物完整性和证据留存。MemGuardOS 已经有 SHA-256、manifest、审计链、CI、测试报告和提交包检查；如果继续冲“企业级可交付”，最值得补的是 SBOM/依赖清单、安全扫描说明、最终同一 Git HEAD 证据复跑，而不是继续添加大量无关 UI。

Agent 记忆研究和产业资料普遍强调语义记忆、情景记忆、程序性记忆、工作记忆之间的分层，以及用户可控、可解释、可删除的长期记忆治理。MemGuardOS 已经实现三类长期记忆和三阶段上下文，后续提升重点应放在更多真实 Agent 行为样例、重复运行稳定性、记忆价值指标和遗忘前后行为对比。

## 3. 赛题评分视角的剩余风险

### 3.1 P0：提交前必须完成

1. 统一正式文档指标口径。正式材料应统一使用本地 `200 passed, 1 skipped` 与 openKylin `195 passed` 的最新口径；任何历史测试数量只能出现在原始证据或历史说明中，不能作为当前结论。
2. 修正旧证据数量表述。最新记忆价值证据中的 openKylin pytest 输出为 `195 passed`，正式材料应直接引用该输出，而不是使用早期统计口径。
3. 更新 `.deb` 交付状态表述。当前 `.deb` 已构建并在 openKylin 维护模式完成 apt 安装复验；后续只能说“若进入产品化发行，可继续申请 openKylin 官方扩展/仓库渠道”，不能说尚未制作 `.deb`。
4. 最终提交前重新生成提交包，并再次运行 inspect/smoke，确保提交包包含最新文档、扩展证据和清单。
5. 在最终冻结代码后，如时间允许，重新在 openKylin 按同一 Git HEAD 复跑证据采集，避免“证据 HEAD 早于最新代码”的追问。

### 3.2 P1：明显提高竞争力

1. 补充供应链与企业级交付证据，包括 SBOM 或依赖清单、安全扫描摘要、发布前检查说明。
2. 真实 Agent 样例可以从 20 组继续扩充到 30 组左右，重点覆盖失败修复、偏好冲突、跨会话复用、遗忘后再会话和 Agent 自述污染边界。若时间有限，保持 20 组但增加三轮代表性重复运行也有价值。
3. 增加盲测/留出样例，减少“自建 benchmark 过拟合”质疑。留出集不需要很大，关键是明确样例来源、生成方式和未参与调参。
4. 对 Kylin embedding SDK 单独记录冷启动、热启动、fallback 和缓存策略。当前可用性证据足够，但若评委关注 SDK 主路径，应主动解释端侧稳定性优先。
5. Web 控制台继续向产品化靠拢，但不要再加入“答辩页面”“评委页面”这类过程性话术。产品界面应服务管理员、开发者、审计人员和 Agent 使用者。

### 3.3 P2：有时间再做

1. 将更多截图证据自动化为可复现脚本，减少人工截图遗漏。
2. 补充 `.deb` 卸载、升级、回滚自动测试。
3. 增加 API 鉴权错误、审计链篡改、异常输入等更多负例截图。
4. 建立独立的发布标签和 GitHub Release 草稿。

## 4. 下一步立即执行方案

本轮开发优先执行以下事项：

1. 修正正式中文文档中的旧测试数量、旧证据数量和过时交付表述。
2. 增加企业级供应链交付说明和轻量 SBOM 生成脚本，优先基于 Python 标准库和项目元数据生成可审计 JSON，不引入新的重依赖。
3. 将 SBOM/供应链检查纳入 `check_competition_ready.py` 和提交包检查，形成自动门禁。
4. 重新运行文档链接检查、竞赛就绪检查、ruff、compileall、pytest、打包、inspect 和 smoke。
5. 提交并推送，保证 GitHub 分支可回溯。

## 5. 不做或谨慎做的事项

1. 不把真实 Agent 适配层的恢复能力描述成模型原生能力。
2. 不把 BPF LSM 的安全测试文件策略描述成系统级全局生产强制策略。
3. 不把 UKUI/Peony 可见入口描述成官方认证内置插件。
4. 不用伪造截图或手写“通过日志”代替真实运行输出。
5. 不为了看起来复杂而引入数据库、中间件或云端 LLM API，这会破坏端侧轻量和可复现优势。

## 6. 预期验收标准

本轮完成后，应满足以下标准：

1. 正式文档中最新测试数字一致：本地 `200 passed, 1 skipped`，openKylin `195 passed`。
2. 真实 Agent 口径一致：基础 12 组加扩展 8 组，合计 20 组真实 OpenHands 会话，记忆系统层和 Agent 行为层均为 `20/20`。
3. 自检报告保持 P0 全通过，且供应链/交付清单能被自动检查。
4. 提交包可重新生成、可解压、可审计，manifest 与 SHA-256 清单无过期。
5. 答辩材料准确说明边界，不出现“已经生产级全局内核策略”“官方 UKUI 深度内置”“外部 LLM 内置”等无法证明的说法。
