# MemGuardOS 失败样例与边界分析

## 1. 为什么原 benchmark 有多个 1.0000

原 benchmark 的定位是功能正确性验证：确认抽取、检索、敏感阻断、精准遗忘、审计链和 OS 机制的主流程没有断裂。它使用固定样例、固定期望和可复现实验环境，因此多个指标达到 1.0000 是合理的，但这不代表开放世界绝对完美。

EvidenceBench v2 的定位不同。它加入 hard negative、holdout、跨语言、冲突、自然语言精准遗忘和真实 OS Agent 场景，用于暴露边界和降低“只为自建样例调规则”的质疑。v2 报告允许指标低于 1.0000，并要求输出失败样例和原因。

## 2. 典型失败或边界案例

| 编号 | 案例 | 可能原因 | 改进方向 |
|---|---|---|---|
| 1 | 用户表达极其模糊，无法判断要遗忘的是偏好还是知识。 | 自然语言缺少主题、类型或范围。 | Erasure Intent Compiler 保持低置信度，要求 dry-run 和人工确认。 |
| 2 | 英文历史案例没有明显实体，中文查询召回弱。 | 跨语言词面重叠低，轻量 hash/FTS 难以泛化。 | Kylin SDK 重排作为可选增强，或加入离线同义词表。 |
| 3 | 工具结果缺少 `state_before/state_after/lesson`，程序性记忆价值下降。 | 只有 stdout/stderr，缺少状态-动作-结果结构。 | Agent bridge 继续强制补齐结构化字段。 |
| 4 | BPF LSM 默认只拦截测试路径或配置路径。 | 当前内核态策略不做任意内容语义识别。 | 保持 BPF 路径强制拦截，内容语义治理放在应用层。 |
| 5 | Kylin SDK 首次推理尾延迟高。 | 端侧模型冷启动和 runtime 初始化较慢。 | 登录后低优先级预热，默认主路径保留 FTS/hash/graph fallback。 |
| 6 | 外部 Agent 自身日志仍保存原始对话。 | 外部日志不属于 MemGuardOS 受管存储。 | 文档和演示明确要求单独清理外部 Agent persistence。 |
| 7 | VM 快照或块设备取证恢复旧数据。 | 逻辑遗忘不等于介质级清除。 | 使用加密擦除或系统级介质清除流程作为企业增强。 |
| 8 | 过宽自然语言遗忘请求可能误伤。 | 请求缺少作用域或保留约束。 | 必须先 dry-run，展示候选和保留项后再确认。 |
| 9 | 相似服务名、文件名或 token 字样导致敏感误报。 | 规则型检测存在词面歧义。 | hard negative 扩充、文档占位符白名单和自定义规则校验。 |
| 10 | openKylin 桌面增强项在非 UKUI 环境不可见。 | Peony/UKUI 插件依赖目标桌面环境。 | 脚本 graceful fallback，最终证据在 openKylin 实机或虚拟机采集。 |

## 3. 不可恢复遗忘边界

MemGuardOS 的遗忘保证范围是受管记忆：SQLite 元数据、FTS 索引、图谱索引、搜索缓存、mmap 段文件 compact 后的受管明文，以及相关审计链。它不能单方面保证 SSD 物理残留、VM 快照、文件系统备份、终端历史、外部 Agent 日志和云端模型日志不可恢复。

## 4. BPF LSM 与 Kylin SDK 边界

BPF LSM 用于证明 OS 级强制拦截能力，默认策略只拦截配置路径和测试路径，不应宣传成通用内核态 DLP。Kylin SDK 是 openKylin 端侧智能检索增强，已验证真实 768 维推理；但默认检索路径仍保留稳定 fallback，以避免冷启动尾延迟影响核心体验。

## 5. v2 复验方式

```bash
python scripts/build_evidencebench_v2.py
python scripts/run_evidencebench_v2.py --output docs/eval_v2_result.json --markdown docs/eval_v2_report.md
```

报告中的失败样例应被保留，而不是删除。它们用于说明边界、定位下一步优化方向，并向评委证明项目没有把固定样例成绩包装成开放世界绝对能力。
