# 科研期刊绘图规范与图包重构依据

本文档记录 MemGuardOS 图表包从“答辩信息图 / dashboard 风格”重构为“科研期刊图件风格”的依据、约束和执行标准。它的作用不是替代项目技术报告，而是说明图件为什么这样画、数据从哪里来、哪些图是定量证据、哪些图只是方法示意，避免后续汇报时把图件性质说错。

## 1. 调研来源

本轮重构参考了 Plottie 的论文图检索思路、官方期刊规范和开源科研绘图代码范式。外部代码库仅作为学习参考，保存在 `external_references/figure_style_research/`，不进入正式竞赛提交包。由于 `figures4papers` 本地仓库未提供 LICENSE 文件，本项目不直接复制其整段实现代码，而是学习其绘图思想、布局范式、字体大小、轴线风格、配色规律和导出习惯，再以本项目真实数据重新实现；`Show2Know` 为 Apache-2.0，`nature-skills` 为 MIT，可作为规范和基础模式参考。

已经拉取并学习的三个重点仓库如下：

## 2. 全局图件标准

图件生成主入口为 `scripts/generate_figures4papers_style_figures.py`，它复用 `scripts/generate_plottie_publication_figures.py` 的图件注册与证据加载逻辑，输出目录为 `outputs/可视化证据包_figures4papers_style/`。旧版图包产物若仍存在，只作为历史对照材料保留；正式报告、答辩 PPT 和交付说明优先使用 figures4papers style 版本。

本项目采用 Python/matplotlib 作为唯一绘图后端。不同图件类别拆分到独立代码文件：方法示意和诊断矩阵在 `scripts/plottie_figures/method_schematics.py`，定量结果图在 `scripts/plottie_figures/quantitative_results.py`，真实截图 image plate 在 `scripts/plottie_figures/image_plates.py`，共享的尺寸、字体、配色、导出、manifest 和 Figure Contract 逻辑在 `scripts/plottie_figures/style.py`。这种结构避免所有图堆在一个大脚本里，也便于后续针对某一类图单独维护。

脚本统一设置白色背景、粗轴线、无右上边框、无图例框、可编辑矢量文字和 300 dpi PNG/TIFF 导出。每张图在绘制前写入一条 Figure Contract，包括核心结论、图件类型、证据链和风险控制，并自动输出到 `outputs/可视化证据包_figures4papers_style/逐图设计契约.md`。

画布尺寸采用 figures4papers 常见的宽幅论文图策略，而不是网页 dashboard 尺寸。主复合图采用约 `14 × 4.8 inch` 或 `14 × 6.2 inch` 的宽幅画布，适合技术报告、答辩 PPT 和论文式报告中横向叙事；单图使用约 `7 × 4.7 inch`。脚本不使用 `bbox_inches='tight'` 改变画布尺寸，避免图件插入 Word、PDF 或论文式报告后尺寸漂移。

配色遵循“低色彩、强证据”的原则。默认使用黑色、深灰、浅灰、深蓝 `#0F4D92`，并少量使用 figures4papers 风格中的绿色、粉红/红色表示混合检索、文本基线、P99 或阈值。深蓝用于项目主方法、通过状态或关键证据；红色只用于失败、风险、尾延迟或强调阈值。图件不使用 rainbow、红绿唯一编码、渐变卡片、大面积色块和 dashboard 指标卡。

中文图件优先使用 CJK sans 字体，例如 Noto Sans CJK、Source Han Sans、WenQuanYi Micro Hei、DengXian 或 SimHei，避免 Arial 无法显示中文而造成 SVG/PDF/PNG 缺字。脚本会优先选择不会触发 PDF 子集化提示的字体；若在其他系统上只能使用 Microsoft YaHei 或 SimSun，可能出现 `MERG NOT subset` 字体提示，这类提示不代表缺字或生成失败，应以 PNG/PDF 实际渲染为准。

## 3. 图件分类与证据边界

本图包分为三类。

第一类是方法示意图，包括 F01-F09、F16、F18。这类图说明系统结构、处理链路、状态机、SDK fallback 和交付审计路径。它们不是性能指标，不应在答辩中说成“实测曲线”。设计上采用点线、时间线、轻量网络、矩阵和列表，避免像网页组件一样堆矩形卡片。

第二类是定量结果图，包括 F10-F15。这类图只使用项目已有 JSON、测试报告和 openKylin 证据文件，不生成项目不存在的数据。F10 展示竞赛就绪门禁，F11 展示 benchmark 构成，F12 展示核心质量指标和检索 ablation，F13 展示延迟和资源，F14 展示存储占用，F15 展示 OS 机制覆盖。所有定量图均在图脚写明数据来源，并在 `outputs/可视化证据包_figures4papers_style/source_data/` 中生成对应 CSV，便于论文式报告和答辩复核。

第三类是截图证据 plate，包括 F17、F19、F20。它们只使用实际生成的截图证据。为了让图面可读，脚本会裁剪截图中的关键区域，但不伪造、不改写、不重绘截图内容。完整截图仍保留在原截图证据包中。

## 5. 不绘制的图

本项目没有训练过程，因此不绘制 loss/accuracy 曲线。本项目没有分类概率排序任务，因此不绘制 PR/ROC 曲线。本项目没有外部数据库加速指标或公开 leaderboard，因此 F12 的 1.0 指标只表述为本项目确定性 benchmark 结果，不表述为公开榜单领先。

这种克制是为了避免“图很好看但证据不真实”的风险。比赛答辩中可以主动说明：图包只展示项目真实实现和真实证据，缺失的图不是遗漏，而是因为项目没有对应实验范式。

## 6. 后续维护建议

新增图件时必须先写清图的论证目的、数据来源和图型选择，再写代码。凡是没有真实数据来源的图，不应放入定量结果目录。凡是截图证据图，应保留原图路径并在 manifest 中记录来源。凡是用于技术报告或最终提交材料的图，优先使用 SVG/PDF；PPT 可使用 PNG；长期归档可使用 TIFF。若是定量图，应同步导出 source data CSV，并在图脚标注来源路径。

如果未来增加更真实的 benchmark，例如真实 shell history、真实 auditd 日志、真实工具调用失败修复轨迹，可以继续扩展 F11-F13 或新增单独的数据图。但新增图仍应遵循同一套尺寸、字体、配色和证据边界。
