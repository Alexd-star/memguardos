## 3. High-priority Gaps For Full-score Target

### P0: openKylin Real Validation

Cannot be fully solved on the current Windows environment. Must run:

```bash
bash scripts/openkylin_verify.sh
sudo bash scripts/install_openkylin.sh "$(pwd)"
journalctl -t memguardd -n 50
sudo bash scripts/install_auditd_rules.sh "$(pwd)"
```

### P0: First-class Tool-result Ingestion

The original plan emphasizes tool execution results. Current implementation can ingest text/file, but lacks a structured tool trace parser. This should be implemented next because it is central to OS Agent memory.

### P0: Explicit Memory Subtype

Current `type` supports `preference`, `knowledge`, and `sensitive_policy`, but the plan requires output style, user habit, tool preference, security policy, workflow, case, template, tool trace. Add a `subtype` field and lightweight classifier.

### P1: Baseline Comparison

Evaluation currently reports only MemGuardOS metrics. Full-score reporting should include simple baselines:

- text-only search;
- hybrid without graph;
- full MemGuardOS.

### P1: Real Embedding / Multilingual Retrieval

Current retrieval uses hashed-vector scoring plus translation hints. This is acceptable for a lightweight prototype, but full-score competition reporting should add a real multilingual embedding backend or clearly present it as future work.

### P1: Real OS Producer

Current auditd rules and OS event ingestion are ready, but real Linux event ingestion must be validated on openKylin. fanotify/eBPF can be a later enhancement if openKylin supports it.

## 4. Best-practice Notes

1. Do not let LLM directly perform irreversible deletion.
   - Current design is good: dry-run, confirm, tombstone, compact, verify.
2. Keep dangerous OS operations behind explicit scripts.
   - Current design is good: auditd/systemd install scripts require user invocation.
3. Keep benchmark generation reproducible.
   - Current data is checked in as JSONL.
4. Avoid overclaiming.
   - Current docs clearly mark rule-based extraction and openKylin pending validation.
5. Preserve test-driven development.
   - Every new capability should add tests and update `docs/测试报告.md`.
